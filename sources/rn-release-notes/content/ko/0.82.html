블로그 번역은 2025-10-08 최초 발표 당시의 설명을 보존합니다. 본문의 “최신 버전”, 지원 상태, 출시 예정 안내와 실험 기능 설정도 발표 당시 기준입니다.

현재 조사 결과는 0.82.x 패치 내역과 사전 배포 기록에 별도로 표시했습니다. 확인한 가장 최근 정식 패치는 0.82.1입니다.

오늘 React Native 0.82를 배포합니다. 새 아키텍처에서만 실행되는 첫 React Native 버전입니다.

이번 배포는 React Native의 중요한 전환점입니다. 새로운 시대의 시작이라고 생각합니다. 이후 버전에서는 기존 아키텍처의 남은 코드를 제거하여 설치 크기를 줄이고 코드 구조를 단순하게 만들 예정입니다.

0.82에는 새 Hermes 버전인 Hermes V1을 선택하여 사용할 수 있는 실험 기능도 포함됩니다. React 버전을 19.1.1로 올려 여러 React 기능을 사용할 수 있게 했습니다. DOM 노드 API도 지원합니다.

새 아키텍처만 사용

React Native 0.76에서 새 아키텍처가 React Native의 기본 아키텍처가 되었다고 발표했습니다.

그 이후 새 아키텍처를 시험하고 개선했습니다. 이제 이번 버전과 이후 버전에서 새 아키텍처를 유일한 아키텍처로 사용할 수 있다고 판단했습니다.

따라서 Android에서 newArchEnabled=false를 설정하거나, iOS에서 RCT_NEW_ARCH_ENABLED=0으로 CocoaPods를 설치해도 이 설정은 무시됩니다. 앱은 계속 새 아키텍처에서 실행됩니다.

이전 방법

프로젝트를 아직 새 아키텍처로 이전하지 않았다면 먼저 React Native 0.81 또는 Expo SDK 54로 이전할 것을 권장합니다. 이 버전들은 기존 아키텍처를 사용할 수 있는 마지막 버전입니다. 새 아키텍처로 이전하는 데 도움이 되는 경고와 성능 개선이 포함됩니다.

다음으로 0.81에서 새 아키텍처를 켜고 앱이 정상적으로 작동하는지 확인하세요. 0.81에서 새 아키텍처를 사용하게 되면 React Native 0.82로 안전하게 올릴 수 있습니다. 0.82에서는 기존 아키텍처를 켤 수 없습니다.

호환되지 않는 외부 라이브러리 때문에 새 아키텍처로 이전할 수 없다면 해당 라이브러리 관리자에게 직접 문의할 것을 권장합니다.

React Native 코어의 버그 때문에 이전할 수 없다면 이슈 추적 시스템으로 알려 주세요.

상호 운용 계층과 외부 라이브러리 호환성

상호 운용 계층은 당분간 코드에 유지합니다. 이 계층에 필요한 모든 클래스와 함수도 가까운 시일 안에 제거하지 않습니다. 상호 운용 계층의 제거에 관한 추가 소식은 이후에 공유하겠습니다.

두 아키텍처 모두와 호환되는 외부 라이브러리가 새 아키텍처만 사용하는 0.82에서도 계속 작동하는 것을 확인했습니다.

기존 아키텍처 클래스 제거

이전 버전과의 호환성을 유지하고 호환성이 깨지는 변경을 줄이기 위해, 이번 버전에서는 React Native 코어에서 기존 아키텍처의 API를 제거하지 않습니다. 기존 아키텍처를 제거하면 전체 번들 크기를 크게 줄일 수 있습니다. 따라서 제거 작업은 다음 React Native 버전부터 시작할 예정입니다.

자세한 내용은 RFC0929: React Native의 기존 아키텍처 제거에서 확인할 수 있습니다.

실험 기능 — Hermes V1

React Native 0.82에서는 Hermes V1을 선택하여 사용할 수 있습니다.

Hermes V1은 Hermes의 다음 발전 단계입니다. 내부 앱에서 시험해 왔으며, 이제 커뮤니티에서도 시험할 수 있습니다. 컴파일러와 가상 머신(VM)을 개선하여 Hermes의 성능을 높였습니다.

초기 시험과 성능 측정에서 Hermes V1은 여러 상황에서 현재 Hermes보다 좋은 결과를 보였습니다. 번들 로딩 시간과 상호 작용이 가능해질 때까지의 시간(TTI)이 줄었습니다. 개선 정도는 앱의 세부 구현에 크게 좌우됩니다.

실제로 사용되는 복잡한 앱인 Expensify 앱에서 다음 개선을 확인했습니다.

Hermes V1 성능 개선 — Expensify 앱 측정
측정 항목Android (저사양 기기)iOS
번들 로딩 시간3.2% 단축9% 단축
전체 TTI (Total TTI)7.6% 단축2.5% 단축
콘텐츠 TTI (Content TTI)7.2% 단축7.5% 단축

전체 TTI는 번들 로딩 시작부터 앱의 첫 화면이 렌더링되고 상호 작용이 가능해질 때까지의 시간을 측정했습니다.

콘텐츠 TTI는 컴포넌트가 처음 렌더링된 시점부터 해당 컴포넌트와 상호 작용이 가능해질 때까지의 시간을 측정했습니다.

Hermes V1에는 아직 JavaScript를 네이티브 코드로 컴파일하는 기능(이전 이름: Static Hermes)이나 React Native EU 2023에서 발표한 JIT 컴파일 기능이 포함되지 않습니다. 이 기능들은 계속 시험하고 있습니다. 진행 상황에 따라 추가 정보를 공유하겠습니다.

Hermes V1을 켜는 방법

참고

Hermes V1이 실험 단계인 동안에는 React Native를 소스에서 빌드해야 합니다. 이후 React Native 버전에서 Hermes V1이 기본으로 제공되면 이 제한이 없어집니다.

프로젝트에서 Hermes V1을 시험하려면 다음 절차를 따르세요.

  1. package.json의 해당 구역을 수정하여 패키지 관리자가 Hermes V1 컴파일러 패키지의 실험 버전을 사용하게 하세요. 아래 버전 번호 형식은 Hermes V1의 실험 단계에서만 사용합니다.

    package.json — Yarn
    "resolutions": {
    "hermes-compiler": "250829098.0.1"
}
    package.json — npm
    "overrides": {
    "hermes-compiler": "250829098.0.1"
}

  2. Android에서는 android/gradle.properties에 hermesV1Enabled=true를 추가하여 Hermes V1을 켜세요.

    android/gradle.properties
    hermesV1Enabled=true

    또한 android/settings.gradle을 수정하여 React Native를 소스에서 빌드하도록 설정하세요.

    android/settings.gradle
      includeBuild('../node_modules/react-native') {
      dependencySubstitution {
          substitute(module("com.facebook.react:react-android")).using(project(":packages:react-native:ReactAndroid"))
          substitute(module("com.facebook.react:react-native")).using(project(":packages:react-native:ReactAndroid"))
          substitute(project(":packages:react-native:ReactAndroid:hermes-engine")).using(module("com.facebook.hermes:hermes-android:250829098.0.1"))
      }
  }

  3. iOS에서는 환경 변수 RCT_HERMES_V1_ENABLED=1을 설정한 상태로 pod를 설치하여 Hermes V1을 켜세요.

    RCT_HERMES_V1_ENABLED=1 bundle exec pod install

    Hermes V1은 미리 컴파일한 React Native 빌드와 호환되지 않습니다. pod를 설치할 때 RCT_USE_PREBUILT_RNCORE 플래그를 사용하지 마세요.

  4. 앱이 Hermes V1에서 실행되는지 확인하려면 앱 또는 DevTools 콘솔에서 다음 코드를 실행하세요. 반환된 Hermes 버전은 1단계에서 지정한 버전(250829098.0.1)과 같아야 합니다.

    // Hermes V1에서는 "250829098.0.1"을 반환해야 합니다.
HermesInternal.getRuntimeProperties()['OSS Release Version'];

React 19.1.1

이번 React Native 버전에는 발표 당시 최신 React 안정 버전인 React 19.1.1이 포함됩니다.

이 React 버전은 React Native의 소유자 스택(Owner Stack)을 완전히 지원합니다. React Native 0.80에 React 19.1.0 지원을 추가했을 때는 @babel/plugin-transform-function-name Babel 플러그인을 사용하면 소유자 스택을 완전히 지원하지 못한다고 설명했습니다. 이번 버전은 이 제한을 없애 모든 React Native 사용자가 소유자 스택을 사용할 수 있게 합니다.

React 19.1.1은 React Native의 Suspense 경계에서 useDeferredValue와 startTransition가 더 안정적으로 작동하게 합니다. 이 두 기능은 앱의 응답성을 높이는 핵심 React 기능입니다. 이전에는 React Native에서 Suspense 경계와 함께 사용하면 대체 화면(fallback) 컴포넌트가 잘못 표시되었습니다. React 19.1.1에서는 웹과 같은 방식으로 일관되게 작동합니다.

DOM 노드 API

React Native 0.82부터 네이티브 컴포넌트는 ref를 통해 DOM과 유사한 노드를 제공합니다.

이전에는 네이티브 컴포넌트가 measure, setNativeProps와 같은 소수의 메서드만 있는 React Native 전용 객체를 제공했습니다. 이번 버전부터는 DOM API의 일부를 구현한 노드를 제공합니다. 웹과 같이 UI 트리를 탐색하고 레이아웃을 측정하는 등의 작업을 할 수 있습니다. 다음은 예제입니다.

function MyComponent(props) {
  const ref = useRef();

  useEffect(() => {
    const element = ref.current;

    // 새 메서드와 속성
    element.parentNode;
    element.parentElement;
    element.childNodes;
    element.children;
    const bounds = element.getBoundingClientRect();
    const doc = element.ownerDocument;
    const maybeElement = doc.getElementById('some-view');

    // 기존 메서드도 계속 사용할 수 있습니다.
    element.measure((x, y, width, height, pageX, pageY) => {
      /* ... */
    });
  }, []);

  return <View ref={ref} />;
}

또한 Text 컴포넌트가 생성하는 말단 텍스트 노드와 React Native 루트 노드를 나타내는 문서 노드에도 접근할 수 있습니다.

새 노드는 measure와 같은 기존 메서드도 계속 구현합니다. 따라서 이 변경은 이전 버전과 호환됩니다.

자세한 내용은 노드 문서를 확인하세요.

기타 변경 사항

Web Performance API (Canary)

React Native는 이제 웹 성능 API의 일부를 구현합니다.

  • High Resolution Time: performance.now()와 performance.timeOrigin을 정의합니다.
  • Performance Timeline: PerformanceObserver와 performance 객체에서 성능 항목에 접근하는 메서드(getEntries(), getEntriesByType(), getEntriesByName())를 정의합니다.
  • User Timing: performance.mark와 performance.measure를 정의합니다.
  • Event Timing API: PerformanceObserver에 보고하는 event 항목 유형을 정의합니다.
  • Long Tasks API: PerformanceObserver에 보고하는 longtask 항목 유형을 정의합니다.

이 API를 사용하면 앱 실행 중 여러 성능 지표를 추적하여 원격 측정에 사용할 수 있습니다. 이후 React Native 버전에서 제공할 React Native DevTools의 Performance 패널에도 표시할 예정입니다.

발표 당시에는 Canary 배포 단계에서만 사용할 수 있습니다. 이후 React Native 버전에서 안정 기능으로 제공할 예정입니다.

Android의 최적화된 디버그 빌드 유형

React Native 0.82부터 debugOptimized 빌드 유형을 사용하여 개발 중 실행 성능을 높일 수 있습니다.

기존 Android는 기본 빌드 변형 두 가지를 만듭니다.

  • debug: 개발할 때 기본으로 사용합니다. React Native DevTools, Metro, Android JVM 디버거, C++ 디버거 등 여러 디버깅 도구에 연결할 수 있습니다.
  • release: 앱을 사용자에게 배포할 때 사용합니다. 완전히 최적화되며, 난독화와 최적화 때문에 디버깅이 어려워집니다.

대부분의 React Native 개발자는 개발 중 C++ 디버거가 필요하지 않습니다. 따라서 debugOptimized 빌드 유형을 도입했습니다.

debugOptimized는 여러 C++ 최적화를 켠 React Native 빌드를 실행하므로 애니메이션과 재렌더링이 더 빠릅니다. 동시에 React Native DevTools로 JavaScript 코드를 계속 디버깅할 수 있습니다.

debugOptimized에서는 C++ 네이티브 디버거를 사용할 수 없습니다. C++ 디버거가 필요하면 debug 빌드 유형을 사용하세요.

앱을 debugOptimized 변형으로 실행하려면 다음 명령을 사용하세요.

Community CLI
npx react-native run-android --mode debugOptimized
Expo
npx expo run:android --variant debugOptimized
참고

debugOptimized 빌드 유형은 React Native 0.81과 Expo SDK 54에도 적용되었습니다.

아래 예제는 화면에서 여러 애니메이션을 렌더링할 때 debugOptimized가 작동하는 모습을 보여 줍니다.

debug 빌드는 약 20FPS로 실행되고, debugOptimized 빌드는 약 60FPS로 실행됩니다.

호환성이 깨지는 변경

처리하지 않은 Promise 거부를 console.error로 보고

이전 버전에서 처리하지 않은 JavaScript 오류의 보고 방식을 개선했습니다. 이제 처리하지 않은 Promise 거부도 같은 방식으로 보고합니다.

이전에는 버그 때문에 이 오류들이 모두 무시되었습니다. 따라서 React Native 0.81로 업그레이드한 뒤에는 기존 오류가 표시될 수 있습니다. 같은 이유로 백엔드에 보고하는 JavaScript 오류에도 기존 오류가 나타나 새 보고 건수가 급증할 수 있습니다.

번역 참고

위 문단의 “0.81”은 공식 0.82 발표 원문의 표기입니다. 이 문서는 원문 버전 번호를 보존합니다.

그 외 호환성이 깨지는 변경

공통

  • ReactNativeFeatureFlags를 src/private로 옮겼습니다. 비공개 API이므로 이 API에 의존하지 않아야 합니다.
  • Appearance.setColorScheme()의 타입을 변경하여 null 값을 허용하지 않습니다. 색상 모드를 초기화해야 할 때는 null 또는 undefined 대신 'unspecified'를 사용하세요.

iOS

  • RCTDisplayLink가 기존 API인 RCTModuleData를 사용하지 않도록 이전했습니다. RCTModuleData는 이후에 제거할 예정입니다.

Android

  • 실수로 public으로 공개했던 com.facebook.react.bridge.JSONArguments 클래스를 제거했습니다.
  • MessageQueueThreadPerfStats를 사용 중단(deprecated) 상태로 지정하고 최소 구현(stub)으로 대체했습니다. 제공하던 통계가 신뢰할 수 없으므로 이 API의 통계에 더 이상 의존하지 마세요.
  • Gradle을 8.x에서 9.0.0으로 올렸습니다. Gradle 9.0.0의 전체 변경 목록은 Gradle 안내에 있습니다. 사용자에게는 영향이 없을 것으로 예상합니다.

C++

  • CallbackWrapper.h와 LongLivedObject.h의 이전 버전 호환용 헤더를 제거했습니다. 올바른 포함 경로는 #include <react/bridging/LongLivedObject.h>와 #include <react/bridging/CallbackWrapper.h>입니다. 이전 경로인 #import <ReactCommon/….h>를 사용하지 마세요.

호환성이 깨지는 변경의 전체 목록은 0.82 CHANGELOG에서 확인하세요.

감사의 말

React Native 0.82에는 93명의 기여자가 만든 868개 이상의 커밋이 포함됩니다. 모든 분의 작업에 감사드립니다.

이번 버전에 중요한 기여를 한 다음 커뮤니티 구성원에게 특별히 감사드립니다.

  • Dawid Małecki, Jakub Piasecki: Hermes V1 도입 지원.
  • Krystof Woldrich: 처리하지 않은 Promise 거부가 무시되는 문제의 수정 지원.
  • Riccardo Cipolleschi: 위 React 19.1.1과 Hermes V1 설명 작성 지원.
  • Rubén Norte: DOM API와 Performance API 설명 작성 지원.
  • Tomasz Zawadzki: debugOptimized 성능 측정 지원.

0.82로 업그레이드하기

기존 프로젝트에서는 React Native Upgrade Helper로 React Native 버전 간 코드 변경을 확인하세요. 새 버전으로 업그레이드하는 방법도 함께 확인하세요.

새 프로젝트를 만들려면 다음 명령을 사용하세요.

npx @react-native-community/cli@latest init MyProject --version latest

Expo를 사용한다면 React Native 0.82는 expo@canary 배포에 포함될 예정입니다.

다음 SDK인 SDK 55는 다음 React Native 안정 버전인 0.83과 함께 제공될 예정입니다.
